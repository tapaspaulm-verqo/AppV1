Verqo · v2a rebuild

One API, three clients, a boundary between what's real and what's mocked

Angular and Flutter both call a single .NET 8 API inside Kubernetes. Inside that API, dependencies only point inward toward Domain — which is also why parts of this codebase could be compiled and tested without network access, and parts couldn't.

Client tier

Angular 18 (standalone components) builds to static assets served by Nginx. Android and iOS ship from one Flutter/Dart codebase, calling the same /api/v1 surface as the browser — no client-specific backend logic anywhere.

Kubernetes runtime

Both pod sets scale independently via HPA. Images are built and the NuGet-dependent layers (Verqo.Infrastructure, Verqo.Api, the xunit suite) restored and tested by GitHub Actions CI before a helm upgrade ships a release here.

Data & external tier

No database runs inside the cluster — deploy/helm/verqo only references an external connection string. Aadhaar is never stored in full: last-4 plus a salted hash, per the Aadhaar Act's storage restriction.

Full rationale and the sandbox-verification status of each layer: docs/ARCHITECTURE.md in the verqo-dotnet repo (§6–§7).
